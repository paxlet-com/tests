# Autonomy measurements — 2026-09-24

The shell pipeline works on fixed workloads, but these results do **not** establish
reliable general autonomy or test the full Taskand planner/orchestrator.

## Validation

- Existing baseline: 5/5 local tests, 3.150 s. Its code-tampering assertion was
  silently skipped because it searched for `steps/*.py` rather than `task.py`.
- Hardened suite: 7/7 local (1.686 s) and 7/7 Docker (3.926 s). This includes
  mandatory tampering, receipt input/output hashes, workspace traversal/symlink
  rejection, build/run separation, and stopping dependent steps after exit 7.
- Docker initially exposed the CLI's fixed audit-store location. Tests now copy
  explicit source directories into temporary storage, excluding `.env` and log
  state. No host checkout mount or published port is required.
- Governance gate: zero errors and warnings.

## Offline mechanism benchmark

Five repetitions × three tasks × three routes; **45/45 verified outcomes** in
both local and Docker runs. Refusal controls: **5/5** in each environment.

| Route | Docker median | Docker p95 | Model calls across 15 tasks |
| --- | ---: | ---: | ---: |
| Exact catalog alias | 107.5 ms | 126.8 ms | 0 |
| Scripted generation | 102.4 ms | 126.1 ms | 15 simulated |
| Scripted repair | 108.9 ms | 165.0 ms | 30 simulated |

Local catalog median was 138.3 ms. These are small workloads with different
host/container environments, not a fair throughput comparison. Scripted model
responses carry no network/model latency or token cost. A successful repair
uses two responses; exhausted validation stops after three. Clarification stops
after one response; an unknown alias without a model stops before any call.

## Live GLM-5.3 probe

Repair disabled; one request per attempt; generated plans execute only in
restricted offline containers. First series:

| Task | Verified outcome | Planning | Container run including startup | Tokens |
| --- | --- | ---: | ---: | ---: |
| Sum 1…100 | Pass | 18.65 s | 2.07 s | 1579 |
| Sort 7,2,9,2 | Not verified: output was not parseable as JSON | 29.11 s | 0.93 s | 2566 |
| Uppercase Polish text | Pass | 24.68 s | 1.34 s | 1821 |

The sorting prompt did not specify JSON; this was an ambiguous test contract,
not proof that the numbers were sorted incorrectly. The initial probe did not
retain the output, so its semantic correctness cannot be recovered.

A single follow-up explicitly requested a JSON array. It failed during planning
with `ValueError`, before execution (23.02 s, 2363 tokens). The exception detail
was deliberately not logged; the precise invalid-plan cause remains unproven.
The harness now records stage, bounded output preview, and safe validation-error
codes for future diagnosis. No repeated calls were made merely to obtain green
results. Total provider requests: **4**, reported tokens: **8329**; monetary cost
was not measured.

## Conclusions and next investigation

1. Exact catalog reuse avoids model calls and is suitable for recurring known
   tasks. A catalog match still requires reviewed content and execution policy.
2. Planning latency dominates these live examples. Scripted repair tests prove
   bounded control flow, not that a live model can repair the sorting failure.
3. Next live investigation: capture safe validation diagnostics for the sorting
   case, then compare bounded repair against no repair using the same task set.
4. Still unmeasured: full planner→validator→orchestrator behavior, concurrent
   tasks, long-lived recovery and descendant termination after runtime timeout.
5. Package digests and unsigned receipts are not OS isolation or trusted approval.
